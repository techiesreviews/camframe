# Experiment: Native GPUI and GPUI Kit port

- **Date started:** 2026-09-30
- **Owner:** Lex (requester); Claude Code implementation with GPT-6-Sol review via Codex CLI
- **Status:** Abandoned on 2026-10-13 at Lex's request
- **Related issue/PR/ADR:** none yet; branch `experiment/gpui-port`
- **Baseline commit/version:** `84da019` (v0.5.0, Electron 44.4.5)

## Question

Can CamFrame's Overlay be rebuilt as a native Rust application on GPUI (`gpui-pre` 0.3.7) and GPUI Kit (`gpui-kit` 0.7.0) while preserving the product contract closely enough to be worth pursuing over Electron?

## Hypothesis and success threshold

A GPUI port can reproduce the Compact Overlay (shape, size, framing, frame/effects, Inline settings, Scenes, Preferences compatibility) with a smaller footprint than Electron. It passes if, on at least one platform with a real camera:

- the live camera paints at the delivered camera frame rate without visible tearing or growing latency;
- every reachable toolbar action and Inline settings control works;
- Preferences documents round-trip between the Electron and GPUI implementations;
- the platform gaps below are either solvable with small platform shims or are acceptable to the product owner.

## Baseline

Electron v0.5.0 at `84da019`, as specified by `docs/product-spec.md`, `docs/visual-spec.md`, and `docs/data-contracts.md`. No resource measurements were recorded for this baseline.

## Variants

### A: `gpui/` crate (Rust 2024, rustc 1.98.1)

- `settings.rs` ports `src/settings.js` over untrusted `serde_json::Value`, reading and writing the same camelCase `preferences.json` fields, including `presets` and `overlayResolution`.
- `camera.rs` replaces `getUserMedia()` with `nokhwa` 0.10 native backends (V4L2, Media Foundation, AVFoundation) on a dedicated capture thread. Mode choice mirrors ADR 0028's preference order without frame-rate caps. Frames decode to BGRA with pure-Rust `zune-jpeg` (MJPEG) or in-crate YUYV/NV12/RGB conversion, avoiding nokhwa's C libjpeg-turbo build.
- GPUI images cannot source-crop, flip, or be clipped by a rounded transformed parent. The capture thread therefore resamples every frame into the camera surface's device-pixel size, reproducing CSS `object-fit: cover`, `object-position`, and `scaleX(-1) scale(z)` around the crop origin. This departs from the Electron constraint that camera frames stay in native video elements.
- GPUI has no element blur filter. Progressive blur is approximated by a tiny, saturated, shape-masked copy of the framed image with transparent edge padding, which the GPU's linear sampler enlarges into a soft halo.
- `overlay.rs` renders the Overlay with GPUI Kit `Button`, `Select`, `Slider`, `Switch`, `TabBar`, `Input`, `Kbd`, and `Spinner`.
- Preferences are stored under `<config dir>/camframe-gpui/preferences.json` so the experiment never races the Electron app's writes.

## Known platform gaps (source inspection of GPUI 0.3.7)

| Contract | GPUI 0.3.7 status | Port behavior |
| --- | --- | --- |
| Always on top / hidden from taskbar | `WindowKind::PopUp` is topmost + tool window on Windows and a non-activating popup-level panel on macOS. It is override-redirect on X11 and an ordinary toplevel on Wayland. | Uses PopUp. Not topmost on Wayland. Runtime Always-on-top toggle is disabled because window kind is fixed at creation. |
| Move by dragging the camera | `Window::start_window_move()` hands the move to the OS | Replaces 16 ms cursor polling. Does not work for X11 override-redirect windows. |
| Programmatic window position | No public API to move an open window | Saved position is restored only when the window opens. Scene positions are saved but not applied. Top/left resize handles cannot anchor the opposite corner. |
| Click-through transparent chrome | `Window::set_input_region()` is implemented only on Wayland | Wayland idles with input limited to the camera. Windows/macOS/X11 would still block clicks across the whole transparent window. |
| Transparent outer window / decorations | Kit's component plugin supplies an opaque theme background to its Base Root; client decorations can also paint a frame on Linux. Windows reports server decorations regardless of the Client option. | The 2026-10-13 change overrides the Root background with transparent black while retaining Kit layers. Lex reported the corrected Windows build still showed the same opaque surround; the experiment was abandoned. Linux client decoration frames remain. |
| Custom animated Full screen | No window-bounds animation or move API | Uses native `toggle_fullscreen()` with no 280 ms transition. |
| Tray, global shortcuts, Start at login | No GPUI APIs | Not ported. Shortcuts work only while the Overlay is focused. |
| Onboarding, high contrast | Not attempted | Not ported. |

## Method

1. `cargo test` for the pure contracts (settings/Scenes/geometry/framing/mode choice/pixel conversion).
2. `cargo clippy --all-targets -- -D warnings`.
3. Manual run on the requester's Ubuntu 26.04 Wayland session with a real camera. Record the camera, delivered mode, observed smoothness, and every control from the product spec.
4. GPT-6-Sol (Codex CLI) review against the Rust best-practices skill and the Electron contracts.

### 2026-10-13: opaque outer background report

- **Reported observation:** Lex supplied a Windows screenshot showing a live Circle camera inside a black rectangular outer window with a gray rounded outline. The private screenshot stays outside the repository. The Windows build and GPU configuration were not supplied.
- **Source inspection:** `gpui_kit::open_window` creates `gpui_kit::base::Root`; the component `WindowState` plugin gives that Root the opaque theme background. Native `WindowBackgroundAppearance::Transparent` does not override this painted fill. The Overlay itself only paints the camera, effects, and controls.
- **Retained change:** construct the same Base Root through `App::open_window`, explicitly setting `.bg(transparent_black())`. Keep its component plugins so input, selections, popups, dialogs, and notifications retain their normal host. Leave `titlebar: None`, PopUp, and the existing Client decoration request intact.
- **Discarded approach:** switching all platforms to Server decorations does not guarantee a frameless window. Wayland can request native server decorations or fall back to Client on compositors without that extension. The Windows backend does not map this request and already reports server decorations, so the screenshot's gray outline cannot be attributed to Kit's Linux client border. No dependency patch or compositor shim is added.
- **Test coverage:** a headless paint test uses the same native options and Root startup helper as production, with a camera-sized opaque fixture and no capture threads. It checks the unmodified Kit opener paints a window-sized nontransparent quad and the explicit transparent Root does not. A second test checks the dialog layer still renders. `gpui-kit/test-support` is enabled only for development tests; existing runtime dependency versions are retained.
- **Historical verification:** local `cargo test --locked` and `cargo clippy --all-targets --locked -- -D warnings` stopped in `yeslogic-fontconfig-sys` because this Linux host lacks `pkg-config`. Initial Windows CI at `4c39f49` built the runtime and passed 23 tests, but Clippy flagged one unused test import. After removing that import, [final Windows CI run 38370012546](https://github.com/techiesreviews/camframe/actions/runs/38370012546) at `bfe884b` passed the release build, all 23 tests (including both new Root regressions), and Clippy. That run produced the corrected `camframe-gpui-windows-x64` artifact. Independent GPT-6.1-Sol/medium source review found no defects in the initial patch. The [dated verification run](../verification/runs/2026-10-13-gpui-transparent-overlay.md) records the historical commands, artifact metadata, and subsequent failed Windows retest. The experiment is now abandoned; the historical artifact is not a supported distribution.

### 2026-10-13: abandonment and build removal

Lex reported the corrected Windows build was “Still the same” and requested “remove the GPUI build.” The native transparency retest is **Fail (user reported)**. The exact tested executable, Windows version, and GPU configuration were not supplied, so this is not a verified artifact-to-device match. The 23 passing headless tests establish scene composition, not native desktop transparency.

The Windows build workflow is removed from the working tree. Source remains in `gpui/` as an archived experiment; no further GPUI repair or build distribution is planned. Historical CI runs and artifact metadata above remain evidence of the attempted fix, not instructions to download a current build. GitHub workflow disabling, artifact deletion, and task cancellation are tracked separately in the [build removal verification run](../verification/runs/2026-10-13-gpui-build-removal.md).

## Interpretation

The native Windows transparency threshold was not met by the reported corrected build. Passing automated paint tests did not establish native compositor behavior. Lex stopped the experiment instead of continuing platform work.

## Disposition

Abandoned. Keep the source and historical verification evidence; remove automated GPUI builds and distribution. The Electron product remains the supported implementation.
