## Question

Can CamFrame's Overlay be rebuilt as a native Rust application on GPUI (`gpui-pre` 0.3.7) and GPUI Kit (`gpui-kit` 0.7.0) while preserving the product contract closely enough to be worth pursuing over Electron?

## Hypothesis and success threshold

A GPUI port can reproduce the Compact Overlay (shape, size, framing, frame/effects, Inline settings, Scenes, Preferences compatibility) with a smaller footprint than Electron. It passes if, on at least one platform with a real camera:

- the live camera paints at the delivered camera frame rate without visible tearing or growing latency;
- every reachable toolbar action and Inline settings control works;
- Preferences documents round-trip between the Electron and GPUI implementations;
- the platform gaps below are either solvable with small platform shims or are acceptable to the product owner.

## Baseline

Electron v0.5.0 at `84da019`, as specified by `docs/product-spec.md`, `docs/visual-spec.md`, and `docs/data-contracts.md`. No resource measurements were recorded for this baseline.

## Variants

### A: `gpui/` crate (Rust 2024, rustc 1.98.1)

- `settings.rs` ports `src/settings.js` over untrusted `serde_json::Value`, reading and writing the same camelCase `preferences.json` fields, including `presets` and `overlayResolution`.
- `camera.rs` replaces `getUserMedia()` with `nokhwa` 0.10 native backends (V4L2, Media Foundation, AVFoundation) on a dedicated capture thread. Mode choice mirrors ADR 0028's preference order without frame-rate caps. Frames decode to BGRA with pure-Rust `zune-jpeg` (MJPEG) or in-crate YUYV/NV12/RGB conversion, avoiding nokhwa's C libjpeg-turbo build.
- GPUI images cannot source-crop, flip, or be clipped by a rounded transformed parent. The capture thread therefore resamples every frame into the camera surface's device-pixel size, reproducing CSS `object-fit: cover`, `object-position`, and `scaleX(-1) scale(z)` around the crop origin. This departs from the Electron constraint that camera frames stay in native video elements.
- GPUI has no element blur filter. Progressive blur is approximated by a tiny, saturated, shape-masked copy of the framed image with transparent edge padding, which the GPU's linear sampler enlarges into a soft halo.
- `overlay.rs` renders the Overlay with GPUI Kit `Button`, `Select`, `Slider`, `Switch`, `TabBar`, `Input`, `Kbd`, and `Spinner`.
- Preferences are stored under `<config dir>/camframe-gpui/preferences.json` so the experiment never races the Electron app's writes.

## Known platform gaps (source inspection of GPUI 0.3.7)

| Contract | GPUI 0.3.7 status | Port behavior |
| --- | --- | --- |
| Always on top / hidden from taskbar | `WindowKind::PopUp` is topmost + tool window on Windows and a non-activating popup-level panel on macOS. It is override-redirect on X11 and an ordinary toplevel on Wayland. | Uses PopUp. Not topmost on Wayland. Runtime Always-on-top toggle is disabled because window kind is fixed at creation. |
| Move by dragging the camera | `Window::start_window_move()` hands the move to the OS | Replaces 16 ms cursor polling. Does not work for X11 override-redirect windows. |
| Programmatic window position | No public API to move an open window | Saved position is restored only when the window opens. Scene positions are saved but not applied. Top/left resize handles cannot anchor the opposite corner. |
| Click-through transparent chrome | `Window::set_input_region()` is implemented only on Wayland | Wayland idles with input limited to the camera. Windows/macOS/X11 would still block clicks across the whole transparent window. |
| Custom animated Full screen | No window-bounds animation or move API | Uses native `toggle_fullscreen()` with no 280 ms transition. |
| Tray, global shortcuts, Start at login | No GPUI APIs | Not ported. Shortcuts work only while the Overlay is focused. |
| Onboarding, high contrast | Not attempted | Not ported. |

## Method

1. `cargo test` for the pure contracts (settings/Scenes/geometry/framing/mode choice/pixel conversion).
2. `cargo clippy --all-targets -- -D warnings`.
3. Manual run on the requester's Ubuntu 26.04 Wayland session with a real camera. Record the camera, delivered mode, observed smoothness, and every control from the product spec.
4. GPT-6-Sol (Codex CLI) review against the Rust best-practices skill and the Electron contracts.

GPT-6-Sol review (Codex CLI 0.157.1, read-only) raised 14 findings. Fixed: stale frame after camera switch, unbounded capture-thread handoff (now 2 s), decode failures not counted, MJPEG dimensions trusted from metadata, odd-size NV12 indexing, Scene import taking more than six records or rejecting truthy non-object `settings`, and edge-smearing where CSS would show the surface background. The last one exposed an Electron defect, recorded as KG-10. Rejected: `fs::rename` does replace existing files on Windows (`MoveFileExW` with `MOVEFILE_REPLACE_EXISTING`). Deferred: Scene positions (no GPUI move API), locale-aware name matching, UI-thread upload cost (measure first), per-edit full-document sanitization, and handle loss if spawning the successor thread fails.
